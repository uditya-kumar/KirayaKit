electricity readings and carried balances, and a receipt that goes out over

## What it is

Small landlords bill by hand: read each floor's meter, add the rent, add water
and gas, carry over whatever went unpaid, and type the total into WhatsApp. The
messages in [`requirements/Rent Track.txt`](requirements/Rent%20Track.txt) are
that workflow, and the spreadsheet beside them is the ledger it leaves behind.

KirayaKit does the arithmetic, keeps the history per tenant, and produces the
same message it used to replace.

## Architecture

Two moving parts, and no server of ours:

```
Expo app (iOS · Android · web)
        │  Clerk session token on every request
        ▼
Neon Data API (PostgREST)
        │  row-level security, auth.user_id() = the Clerk user
        ▼
Neon Postgres — tables, v_* views, SQL functions
```

Anything that looks like it needs a backend belongs in SQL — a
`security_invoker` view so one request fills a screen, or a function called
through `.rpc()` for a multi-step write. The client holds no secrets: the Neon
Data API URL and the Clerk publishable key are the only configuration it ships
with, and rows are scoped by RLS rather than by a filter in the query.

## Features

**Houses** — list with search and tenant counts, add and edit (name, address,
floor count, UPI ID, GPay number), soft delete. A house cannot shrink below a
floor an active tenant still occupies; the database enforces that, not the form.

**Tenants** — one active tenant per floor per house, with rent, electricity
rate, opening meter reading, move-in date, agreement expiry and contact details.
A tenant screen shows the current month, recent months, and what is outstanding.

**Bills** — one per tenant per month. The form opens on a server-computed draft:
rent and rate snapshotted, the reading the meter counts up from, the balance
carried in, and the existing bill when that month has been billed already. Extra
charges (water, gas, anything) are rows of their own.

**Receipts** — the bill as the tenant receives it, shareable to WhatsApp as
formatted text with the UPI ID and GPay number attached.

**Payment history** — every month for a tenant, newest first, with what was
billed and what was paid.

**Profile** — portfolio totals (properties, tenants, pending), a light/dark
appearance toggle that overrides the device setting, and sign out.

## The billing model

`bills.total_billed` is generated by Postgres, so the total is never something
the client computed:

```
total_billed = rent_amount
             + (current_reading − previous_reading) × electricity_rate
             + extra_charges_total
             + previous_balance
```

Three consequences worth knowing before reading the code:

- **The rate is snapshotted.** Editing a tenant's electricity rate never rewrites
  a bill that has already gone out.
- **Unpaid amounts carry forward.** A month that was not settled arrives in the
  next bill as `previous_balance`, which is why the newest bill's `balance_due`
  is a tenant's _whole_ debt — summing months double-counts it.
- **Readings only move forward,** and a month can be billed once per tenant. Both
  are constraints, not validations.

## Getting started

### Prerequisites

- Node 20.19 or newer
- A [Neon](https://neon.tech) project with the **Data API** enabled
- A [Clerk](https://clerk.com) application, registered with Neon as the JWT
  provider so `auth.user_id()` resolves to the Clerk user id

### 1. Install

```bash
git clone https://github.com/<your-account>/KirayaKit.git
cd KirayaKit
npm install
```

### 2. Configure

Create `.env.local` in the repository root:

| Variable                            | Used by                | Where it comes from                        |
| ----------------------------------- | ---------------------- | ------------------------------------------ |
| `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` | the app                | Clerk dashboard → API keys                 |
| `EXPO_PUBLIC_NEON_DATA_API_URL`     | the app                | Neon dashboard → Data API                  |
| `DATABASE_URL_UNPOOLED`             | the scripts below only | Neon dashboard → connection string, direct |

The two `EXPO_PUBLIC_` values are compiled into the client and are meant to be
public. `DATABASE_URL_UNPOOLED` is not: it is the owner-role connection string,
it never reaches the app, and nothing but the local scripts reads it.

### 3. Set up the database

Apply the migrations in order, then regenerate the types. `pg` is not an app
dependency — it is only needed for schema work, so install it transiently:

```bash
npm i --no-save pg
npm run migrate src/db/migrations/0001_init.sql
npm run migrate src/db/migrations/0002_house_floor_guard.sql
npm run migrate src/db/migrations/0003_bill_form.sql
npm run migrate src/db/migrations/0004_drop_bill_shared_at.sql
npm run gen-types
```

The numbered files are the record of what has been applied; there is no ledger
table. Each file goes to the server in one transaction, so a failure leaves
nothing half-applied.

### 4. Run

```bash
npm start          # dev server; press a / i / w
npm run android
npm run ios
npm run web
```

Sign up in the app and add one house before seeding. Every house and tenant hangs
off a `users` row, and that row is created lazily: the first insert that needs it
fails on the foreign key, `ensure_profile()` runs, and the insert is retried. With
the account in place, the seed fills it with plausible data:

```bash
npm run seed-dev              # seeds the most recently created users row
npm run seed-dev user_2abc…   # or a specific Clerk user id
```

## Project layout

```
src/
  app/                Routes only — one file per screen or layout.
    _layout.tsx         Providers and the auth guards; the only place route access is decided.
    (auth)/             sign-in, sign-up — rendered only when signed out.
    (tabs)/             The signed-in app: houses/ and profile/, each with its own Stack.
  api/                One module per domain noun. Talks to Neon; no React.
  hooks/              use<Thing>.ts — a TanStack Query wrapper per api function.
  components/
    rentComponents/     The app's own presentational components.
  constants/Colors.ts  Every colour in the app. Nothing else holds a hex.
  libs/               Third-party client setup: neon.ts, query-client.ts, clerk-errors.ts.
  types/database.ts   GENERATED from the schema. Never edited by hand.
  utils/format.ts     Display formatting — ₹ amounts, floors, bill months.
  db/migrations/      Numbered SQL. The schema's source of truth.
```

A feature is added in that order: migration → `gen-types` → `api/` → `hooks/` →
screen → component. `@/` is the alias for `src/`.

## Security model

- Every table has RLS enabled and an owner policy keyed on `auth.user_id()`,
  which the Clerk session token supplies. Queries never filter by `owner_id` —
  doing so would read as though the security lived in the client.
- Views are `security_invoker = true`, so a view cannot widen what its caller can
  see.
- Route guards (`Stack.Protected`) keep the UI honest; RLS is the enforcement.
- Signing out clears the query cache — it holds rows returned for a session that
  has ended.

## Design source

The mock is a [Pencil](https://pen.dev) document at `requirements/design file`.
It is encrypted and light-mode only; the dark palette in `Colors.ts` has no node
behind it. Where a screen and the mock disagree, the code says so in a comment
rather than inventing layout quietly.

## Known gaps

- `v_tenant_list.total_pending` sums every month, so it double-counts carried
  balances; screens that need a true figure read the newest bill's `balance_due`.
  A `LATERAL … LIMIT 1` rewrite is pending.
- `charge_presets` is in the schema and in the dev seed, but the app neither
  writes it nor prefills the bill form's "Add charge" from it.
- No portfolio-summary view: the Profile totals are reduced in the client from
  two requests.
